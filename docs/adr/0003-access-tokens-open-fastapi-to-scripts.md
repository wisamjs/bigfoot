# Access tokens open FastAPI to a job seeker's scripts

Amends [ADR 0001](0001-fastapi-behind-nextjs-with-authjs.md). FastAPI used to be reachable only by the Next.js server. A job seeker can now also call it directly, from a script, with an Access token: a long-lived secret they create on the Account page and send as `Authorization: Bearer …`. The first uses read a job seeker's data, such as a local, read-only MCP server (BIG-65); a cron job that adds an Interview when one appears in a calendar needs write access, which comes next (BIG-110). The rest of ADR 0001 stands: the browser still never calls FastAPI, sign-in stays on Auth.js, and FastAPI still scopes every query to one job seeker id. An Access token resolves to the same id a web token carries, so route code doesn't know which kind it was given.

We chose personal tokens over a device-code sign-in or OAuth because a cron job can't sign in interactively: something has to hold a long-lived secret, and a token the job seeker can name, see and revoke is the simplest thing that does. A device-code flow for an interactive CLI can come later and issue these same tokens.

There is one kind of token, with no scopes. For now it only reads that job seeker's Applications and Interviews: every route that changes data, and the Account routes (onboarding, the job seeker's record, deleting the account, managing tokens), accept web tokens only and answer an Access token with 403. So a leaked token can't change data, delete the account or create tokens that outlive its own revocation. Tokens expire a year after they are created, so a forgotten one doesn't work forever.

Bigfoot stores only a SHA-256 hash of each secret and shows the secret once. A fast, unsalted hash is enough because the secret is 256 random bits, not a password a person chose. Secrets are `bigfoot_` followed by 43 URL-safe characters. The prefix lets FastAPI tell the two kinds of token apart without trying both, and FastAPI refuses anything not in that exact shape before querying the database. A secret scanner can find a leaked token only once it is given that pattern (for example, a GitHub custom pattern); none knows it out of the box. Revoking deletes the row; so does deleting the account.

The costs: FastAPI is now a public API, so its routes are a contract with scripts we don't control, and its abuse limits matter. Each Application text field has a maximum length, a job seeker can have at most 1,000 Applications and an Application at most 50 Interviews, so one account can't fill the database; per-IP rate limits are still to come (BIG-19). Once tokens can write (BIG-110), a token without scopes that a script uses only to add Interviews could also delete every Application.
